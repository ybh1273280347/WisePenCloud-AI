# 从 PDF 地狱到临时文件中心化：一次文档解析链路的工程收敛

过去一天，我们围绕 WisePen 的文档解析链路做了一轮非常密集的探索。

一开始的问题看起来很简单：

> 用户上传一个文件，系统怎么又快又稳地把它变成模型能消费的上下文？

但真正做下来才发现，这不是“找一个最强 parser”这么简单，而是一个典型的工程边界问题。

文档解析至少有两条完全不同的链路：

```text
知识库入库链路：
  重质量、重结构、重长期索引、重权限一致性

Python 附件消费链路：
  重速度、重稳定、重即时问答、重模型可读
```

如果把这两条链路混在一起，就很容易陷入一种幻想：找一个万能解析器，所有格式都用它，既快又准又稳定。

但文档解析没有这种银弹。

最后，我们把 Python 附件消费侧的解析策略收敛成了：

```text
PDF：MinerU
DOCX / PPTX：Docling
XLSX：pandas / openpyxl
其他边角格式：Docling -> MarkItDown 兜底
```

不过，这次真正关键的收敛点还不只是 parser 选择，而是 `document_parse` 的定位变化。

我们原先更接近一种“一次性消费”模式：

```text
URL / 内部 ref / 上传文件引用
  -> document_parse 直接消费
  -> 解析完返回 content
```

现在改成：

```text
URL / 内部 ref / 上传流 / fetch 结果
  -> 先 materialize 成真实临时文件
  -> 临时文件保存一天
  -> document_parse 只处理真实临时文件
```

这个变化看起来不大，但它解决了很多后续设计上的难题。

---

## 一、最开始：PDF 解析把我们按在地上摩擦

最初我们对 Docling 抱有很高期待。

Docling 的优势很明显：它能输出结构化 Markdown，能识别标题、段落、表格、图片等文档元素，整体比纯文本抽取强很多。

但很快我们就意识到一个问题：

> PDF 是文档解析里最深的坑。

我们在 PDF 解析上遇到过几类问题：

```text
1. 某些 PDF 页级 preprocess 失败
2. Docling convert 整体成功，但中间页面 skipped
3. 图片遍历导致 Markdown 噪声变多
4. 表格、公式、图文混排场景速度较慢
5. 错误页不会总是抛异常，容易被“成功状态”掩盖
```

最典型的问题是：

```text
Docling 整篇 convert 成功
但某些 page 被标记 failed / skipped
外层 try/except 根本抓不到
```

这意味着不能简单写：

```python
doc = converter.convert(pdf_path).document
markdown = doc.export_to_markdown()
```

然后就相信结果完整。

如果 Docling 要承担 PDF 主链路，就必须做更细的页级质量校验：

```text
Docling 整篇 convert
  -> 逐页检查
  -> 空页 / 异常页 / 内容过短
  -> 页级 fallback
```

但这样链路会越来越复杂。

于是我们开始横向测试其他方案。

---

## 二、MinerU 一开始就很诱人，但 CPU 推理太慢

其实 MinerU 并不是最后才进入视野。

我们一开始就测试过 MinerU，而且它的效果非常诱人。

它更像一个真正的“文档理解工具”，而不是简单的文本抽取器。对于复杂 PDF，它在版面、公式、表格、图片、论文结构上的表现更接近我们想要的结果。

但当时最大的问题是：

> CPU 推理太慢。

对于 Python 附件消费侧来说，速度是非常核心的指标。

用户上传一个附件，是希望马上问、马上答，而不是等待一个重型解析任务跑很久。MinerU 在效果上很有吸引力，但在纯 CPU 条件下，很难作为即时附件消费的默认方案。

我们也考虑过让用户自备 API，走云端文档解析服务。

但这个方案也不适合作为平台主链路：

```text
1. 用户不一定愿意配置额外 API Key
2. 用户配置质量不可控
3. 平台能力不能建立在用户自备服务之上
4. 一旦用户没有配置，主链路就会退化
5. 成本、限流、稳定性都难以统一管理
```

所以 MinerU 当时被暂时搁置。

我们继续测试 Docling、MarkItDown、pdfminer、pdfplumber、PyMuPDF、OnlyOffice 等方案，希望找到一个更轻、更快、工程成本更低的 PDF 路线。

但最后测试一圈下来，结论反而更清楚：

```text
PDF 这件事，轻量方案可以快，但很难好。
MinerU 很重，但它确实更接近 PDF 解析的正确方向。
```

---

## 三、MarkItDown：轻是轻，但 PDF 直接出局

MarkItDown 的优点很明显：轻、简单、调用方便。

```python
from markitdown import MarkItDown

markdown = MarkItDown(enable_plugins=False).convert(str(pdf_path)).text_content
```

但在 PDF 上，它的效果并不能接受。

我们遇到过典型输出：

```text
Long-formfictionwritersneedmemorythatanswersmulti-hopquestions
```

也就是英文空格被直接吃掉。

更糟糕的是，它还会把普通正文误判成 Markdown 表格，产生大量污染性的结构。

这类结果最危险的地方在于：

```text
它不报错
它输出很长
它看起来不是空的
但语义已经坏了
```

这比直接失败更危险。

因为系统会误以为解析成功，然后把错误上下文交给模型。

所以 MarkItDown 最终被踢出 PDF 主链路，只保留为冷门格式的最后兜底。

结论很明确：

```text
MarkItDown 可以兜底杂格式。
但不要用它兜底 PDF。
```

---

## 四、pdfminer 是对的，但不能指望它解决表格

接着我们测试了 PyMuPDF、pypdf、pdfplumber、pdfminer.six 等轻量 PDF 工具。

在一个 23 页论文 PDF 上，轻量文本层抽取速度非常夸张：

```text
PyMuPDF raw text：约 0.05s
pypdf：约 0.3s
pdfplumber：约 1.8s
pdfminer：约 2.0s
```

同一个文件，pymupdf4llm 大约要 20 秒，Docling 大约要 30–45 秒。

这说明一个事实：

```text
对干净文本型 PDF，文本层抽取非常快。

Docling / MinerU 之所以慢，
不是因为文本难抽，
而是因为 layout、table、image、formula、vision pipeline 重。
```

pdfminer 的结果很有启发。

它输出的正文可读性很好，空格正常，页码 marker 也稳定。对于干净文本 PDF，它非常适合作为文本层兜底。

但它的问题也很清楚：

> pdfminer 不是表格语义解析器。

pdfminer 能给我们：

```text
LTTextBox
LTTextLine
LTChar
LTLine
LTRect
LTImage
bbox
font
layout object hierarchy
```

但它不会可靠地告诉我们：

```text
这里是 Table 1
这一行对应哪个表头
这个数值属于哪一列
```

我们尝试用 pdfminer + pdfplumber + tabulate 做 hybrid benchmark。

结果第一版直接烂掉：pdfplumber 的 text strategy 全页扫描，把普通正文页整页误判成表格，甚至重新制造了 MarkItDown 那种空格粘连灾难。

这轮测试最后给出的结论是：

```text
pdfminer 适合作为 PDF 文本层兜底。
pdfplumber / Camelot / PyMuPDF table finder 可以做专项表格插件。
但这条线不适合作为 PDF 主解析器。
```

PDF 主解析仍然需要更强的工具。

---

## 五、OnlyOffice：它是编辑器，不是文档解析器

中途我们也考虑过 OnlyOffice。

但很快发现，OnlyOffice 的定位更接近：

```text
文档编辑
文档预览
格式转换
Office 协作
```

它不是为 RAG / LLM 文档解析准备的。

它可以做：

```text
PDF -> DOCX
DOCX -> HTML
Office 预览
```

但它不适合承担：

```text
PDF -> clean Markdown
PDF -> table / formula / image-aware IR
PDF -> 模型可直接消费的结构化上下文
```

尤其是在 PDF 转 Markdown 这件事上，OnlyOffice 更倾向于保版面，而不是恢复语义结构。

在某些场景下，它会采取类似“把版面转换为图片，再把图片嵌入 Markdown”的策略。

这对预览可能有价值，但对模型消费并不友好。

因为模型需要的不是“看起来像原文档”，而是：

```text
标题是什么
正文是什么
表格是什么
图片和正文有什么关系
页内结构如何组织
```

所以最后确认：

```text
OnlyOffice 不应该进入 PDF 解析主链路。
```

它可以留在文档预览、编辑、格式转换层，但不应该承担解析主职责。

---

## 六、PDF 最终选择：上 GPU 部署 MinerU

测试一圈之后，PDF 解析的方向已经很清楚了：

```text
PDF 太复杂。
轻量库太弱。
Docling 有价值，但不是 PDF 终局。
OnlyOffice 不适合。
MinerU 很重，但效果最接近目标。
```

所以，当具备 GPU 部署能力之后，MinerU 重新回到 PDF 主链路，并成为最终选择。

MinerU 的定位更接近“文档理解工具”，适合处理：

```text
PDF
扫描件
图片型文档
复杂版式
论文
公式
表格
图文混排
```

它重，但 PDF 值得它重。

最终 PDF 策略收敛为：

```text
PDF：
  MinerU primary
  PyMuPDF / pdfminer emergency fallback
```

这里还有一个重要的职责边界：

```text
Python 附件消费侧：
  重即时问答，重快速消费

Java 知识库入库侧：
  重长期质量，重结构完整，重索引可靠
```

对于知识库来说，可以接受更重的解析流程。

但对于 Python 附件消费侧，速度同样重要。PDF 之所以仍然选择 MinerU，是因为 PDF 的质量底线太高，不能用明显损坏语义的轻量方案糊弄过去。

---

## 七、Office 全家桶：Docling 意外地非常稳

PDF 定下来以后，我们重新看 Office。

原本我们担心 PPTX 的图片链路：如果 Docling 只能抽文本，不能保图，那 PPTX 可能还要走更重的视觉解析路线。

于是我们做了专门 benchmark，只测 Docling，不加任何兜底。

测试文件包括：

```text
Chapter4 频域.pptx
中国近现代史纲要_期末开卷资料.docx
```

结果非常理想。

### PPTX 结果

```text
status = ConversionStatus.SUCCESS
pages = 73
tables = 2
pictures = 268

run1 = 16.6137s
run2 = 2.2207s
run3 = 2.1969s
```

冷启动 16 秒，热运行 2.2 秒。

更关键的是：

```text
pictures = 268
```

也就是说，Docling 对 PPTX 图片链路是通的。

它不仅能解析文本，还能识别图片，并导出图片引用。

这直接改变了我们对 PPTX 的判断。

原本 PPTX 可能会被视为“视觉文档”，需要更重的解析工具。但测试结果说明，对于 Python 附件消费侧，Docling 已经足够作为 PPTX 的默认主解析器。

### DOCX 结果

```text
status = ConversionStatus.SUCCESS
markdown_chars = 99114
text_chars = 96450
tables = 134
pictures = 0

run1 = 5.6781s
run2 = 6.4757s
run3 = 7.5664s
```

这个 DOCX 是一份很重的开卷资料，表格数量很多。Docling 能稳定解析出 134 个表格，Markdown 质量也很好。

这说明 Docling 在 DOCX 上也足够稳定。

因此 Office 路线正式收敛：

```text
DOCX：Docling
PPTX：Docling
XLSX：pandas / openpyxl
```

## 八、为什么 XLSX 不走 Docling？

XLSX 是一个特殊情况。

对于 DOCX / PPTX，我们关心的是文档结构、段落、标题、图片、表格和阅读顺序。

但 XLSX 本质上是结构化数据表。

Python 附件消费侧如果要读 Excel，最重要的是：

```text
sheet 名称
行列结构
单元格内容
表头
数值
公式
合并单元格
基础预览
```

这些东西用 pandas / openpyxl 更直接，也更稳定。

所以 XLSX 不进入 Docling 主链路。

最终策略是：

```text
数据型 XLSX：
  pandas / openpyxl

视觉报表型 XLSX：
  后续可考虑视觉解析，但不是默认路径
```

这也是整个解析策略里很重要的一点：

> 不要为了“统一 parser”而牺牲格式本身的语义。

Excel 是表格数据，就应该优先用表格工具读。

## 九、真正的转折：document_parse 不再直接消费 URL 或 ref

在 parser 路线逐渐收敛以后，我们又遇到了一个更底层的问题：`document_parse` 到底应该消费什么？

一开始，我们更接近这种设计：

```text
document_parse:
  接收内部 file_ref
  或接收 direct_url
  然后自己解析
```

这看起来很方便。

用户给一个 URL，工具直接解析。

内部工具生成一个文件，也给 ref 解析。

但这个设计越往后走越别扭，因为它把太多职责塞进了 `document_parse`：

```text
1. 它要理解 URL
2. 它要理解内部 ref
3. 它要关心文件来源
4. 它要处理下载或解析 ref
5. 它要参与临时文件生命周期
6. 它还要承担 parser routing
```

这会让 `document_parse` 逐渐变成一个混合体：

```text
resolver + fetcher + file manager + parser
```

边界开始变脏。

后来我们重新定了一个更干净的前提：

> 系统里的临时文件会保存一天。

这个前提一成立，整个设计就变了。

既然临时文件本来就会保存一天，那么各种来源的文件都应该先被 materialize 成真实临时文件，然后再交给 `document_parse`。

也就是：

```text
用户上传
网页 fetch
论文下载
connector 文件
内部工具产物
  ↓
统一落成真实临时文件
  ↓
document_parse 只解析真实临时文件
```

从此以后，`document_parse` 的定位变成：

```text
document_parse = temporary local file parser
```

它不再是：

```text
URL parser
ref parser
file resolver
document acquisition tool
```

这个定位变化非常关键。

---

## 十、临时文件中心化解决了什么问题？

这个改动看起来只是把文件先落地一天，但它实际上解决了很多工程难题。

### 1. 解析器边界变干净了

`document_parse` 不再关心文件来自哪里。

它只关心：

```text
文件路径
mime type
suffix
file size
page count
parser routing
timeout
parse result
```

这让 parser 的职责非常清晰：

```text
我不负责拿文件。
我只负责解析文件。
```

URL 怎么下载、ref 怎么解析、connector 文件怎么获取，都交给更前面的文件 materialization 层。

---

### 2. 参数协议变简单了

原来为了支持各种来源，`document_parse` 可能需要支持互斥参数：

```text
file_refs
direct_urls
```

这会让工具参数校验越来越复杂。

而现在可以收敛成：

```text
temp_file_id / temp_file_path
```

工具契约简单很多。

这也降低了模型调用工具时选错参数组的概率。

---

### 3. 缓存机制不需要升级成多模态协议

这是一个非常现实的问题。

现有缓存机制适合缓存长文本：

```text
ToolReturn.content
cacheable_texts
```

如果为了图片、表格截图、页面渲染，把 `ToolReturn` 改成复杂结构化多模态对象，整个缓存系统都会被拖下水。

但临时文件保存一天以后，这个问题就变简单了：

```text
document_parse：
  只输出文本
  进入原有文本缓存

图片 / 页面截图 / 视觉信息：
  不进缓存
  需要时从临时文件重新提取
```

也就是说：

```text
文本是可缓存结果。
图片是按需运行时材料。
```

这样缓存机制不用炸。

---

### 4. 图片按需消费不需要提前保存全部图片

PPTX 里可能有很多图片。

我们测试的 PPTX 就有：

```text
73 slides
268 pictures
```

如果解析时把这些图片全部保存、全部建立 manifest、全部进入返回协议，工程复杂度会迅速上升。

但如果原始 PPTX 临时文件保留一天，就可以换一种思路：

```text
普通问答：
  使用文本解析结果

用户问图片 / 某页 / 某个图：
  从临时 PPTX 里按需提取相关图片
  用完即丢
```

不需要默认保存 268 张图片。

不需要让缓存层理解图片。

不需要让 `document_parse` 返回多模态结构。

这就是临时文件作为“一日内 source of truth”的价值。

---

### 5. 重试和降级更自然

解析失败并不一定意味着文件不可用。

可能是：

```text
Docling 失败
MinerU 超时
某页解析异常
某个 parser 版本有 bug
```

如果只有一次性 URL 或 ref，重试时还要重新获取文件。

而现在真实临时文件已经落地，重试就简单很多：

```text
同一个 temp file
  -> 换 parser
  -> 换参数
  -> 页级重试
  -> emergency fallback
```

这对 PDF 尤其重要。

---

### 6. 安全边界更清楚

`document_parse` 不再直接碰 URL，也就不需要承担复杂的网络安全风险。

比如：

```text
SSRF
外部 URL 白名单
下载大小限制
重定向处理
鉴权 URL 泄露
connector 权限解析
```

这些都应该属于文件获取层，而不是 parser 层。

parser 层只处理已经通过系统校验、已经落地的临时文件。

这让安全边界也更清楚。

---

## 十一、最终架构：先 materialize，再 parse

最终 Python 附件消费侧可以分成几层：

```text
File Materialization Layer
  负责把各种来源变成一天 TTL 的真实临时文件

Document Parse Layer
  只解析真实临时文件，输出文本

Visual Read Layer
  只在需要时，从真实临时文件抽取图片或页面视觉信息

Cache Layer
  只缓存文本，不缓存图片

Model Runtime
  普通问题吃文本
  视觉问题吃文本 + 临时视觉材料
```

对应链路是：

```text
用户上传 / fetch / connector / 内部工具产物
  ↓
materialize temp file
  ↓
document_parse(temp_file)
  ↓
content / markdown / text
  ↓
cacheable_texts
  ↓
模型普通问答
```

视觉追问则走旁路：

```text
用户问某页图片 / 图表 / 流程图
  ↓
定位相关 page / slide
  ↓
从 temp file 按需抽取视觉材料
  ↓
模型消费
  ↓
临时视觉材料丢弃
```

这套结构里，`document_parse` 的职责非常明确：

```text
它只消费真实临时文件。
它只产出文本解析结果。
它不负责 URL。
它不负责 ref。
它不负责长期资产。
它不负责图片缓存。
```

---

## 十二、最终解析路由

在这个定位变化之上，解析路由也就稳定了：

```text
用户上传附件
  ↓
Materialize 成真实临时文件，保存一天
  ↓
Attachment Parse Router
  ↓
文件类型分流：
  PDF  -> MinerU
  DOCX -> Docling
  PPTX -> Docling
  XLSX -> pandas / openpyxl
  TXT / MD / JSON / YAML / Code -> direct loader
  其他 -> Docling -> MarkItDown
  ↓
统一输出：
  content
  warnings
  parser metadata
  cacheable_texts
```

这个路由背后的原则是：

```text
PDF 用重工具保证质量。
Office 用 Docling 保证稳定和速度。
XLSX 尊重原生结构，用 pandas/openpyxl。
冷门格式先尝试 Docling，再用 MarkItDown 兜底。
document_parse 只处理真实临时文件。
```

---

## 十三、最终结论

这一轮探索最大的收获不是“某个库最好”，而是我们终于把不同工具的职责边界划清楚了。

最终方案：

```text
PDF：
  MinerU

DOCX / PPTX：
  Docling

XLSX：
  pandas / openpyxl

其他冷门格式：
  Docling -> MarkItDown 兜底

文件输入：
  URL / ref / upload / fetch result
  先 materialize 成一天 TTL 的真实临时文件

document_parse：
  只解析真实临时文件
  输出文本 content
  不直接消费 URL / ref
  不承担文件获取职责
```

这套方案的优势是：

```text
1. PDF 质量有保障
2. Office 解析速度快且稳定
3. PPTX 图片链路保留按需扩展空间
4. XLSX 保留原生表格语义
5. 缓存机制继续保持文本缓存，不被多模态结构污染
6. document_parse 边界清晰，不再混入 URL/ref 解析职责
7. 临时文件作为一天内 source of truth，支持重试、降级和按需视觉读取
8. Python 附件消费侧和 Java 知识库入库侧边界清晰
```

最后，这次探索也证明了一点：

> 文档解析不是“找一个万能 parser”，而是围绕业务目标做路由、边界和生命周期设计。

对知识库来说，解析结果要长期稳定、可索引、可追溯。

对附件消费来说，解析结果要快速、干净、能被模型立即消费。

而对工具系统来说，最重要的是不要让一个工具承担太多职责。

`document_parse` 不应该既拿文件、又解析文件、又管理图片、又处理缓存。

它只应该做一件事：

> 解析一个已经存在的真实临时文件。

这个定位一旦明确，很多原本纠缠在一起的问题都会自然解开。
