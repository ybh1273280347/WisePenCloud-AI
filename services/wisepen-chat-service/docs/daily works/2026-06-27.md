# 2026-06-27

今天这轮工作的主线是 WisePen 私有知识库 RAG：先做外部方案和论文调研，再把它们收敛成我们自己的架构，最后和现有工具体系、权限模型、可复用组件对齐。中间也顺手补了前端搜索源配置和 web 缓存文档，但今天真正的重心还是 RAG 方案定稿。

## 今天完成了什么

### 1. 做了一轮 RAG 深度调研

今天先围绕 Chunk RAG、Context Indexing、Concept Graph、GraphRAG/LightRAG、Ragas 等方向做了调研。

最后没有选择引入一个完整 RAG 框架接管主链，而是把结论收敛成：

```text
Chunk RAG 主线
  + Context Indexing
  + Qdrant dense retrieval
  + Elasticsearch lexical retrieval
  + Ranking / Context Builder
  + Concept Graph 旁路增强
```

这个判断的核心原因是：WisePen 已经有自己的工具切面、缓存协议、权限系统、chunking engine 和 ranking engine。直接上 GraphRAG / LightRAG / LlamaIndex 这类完整框架，会让外部框架的 storage、权限、prompt、worker 和评估假设反过来约束我们，得不偿失。

### 2. 对齐了 RAG 权限模型

今天把 RAG 权限边界敲得比较硬：

- Java `wisepen-resource-service` 是唯一权限事实源。
- `resource_id` 是 RAG 权限根。
- 第一版直接使用资源 `VIEW` 作为 RAG 查询准入，不新增 `QUERY` 动作。
- document、document version、parent chunk、child chunk 都继承 resource 权限。
- 不做段落级、父块级、子块级独立 ACL。
- Chat Service RAG 保存预计算 `acl_projection`，作为检索前强制准入条件。

最重要的一条是：

```text
不能先无权限召回 topK，再逐条调用 resource-service 过滤。
```

因为那会让未授权 chunk 先进入 Qdrant/Elastic 结果、fusion、rerank、日志和中间候选，安全边界太晚。

最终定稿为：

```text
Qdrant / Elasticsearch / Mongo / Graph 查询前必须带 ACL filter
  -> 候选 hydrate / rerank
  -> Context Builder 前按 resource_id 批量调用 resource-service 做 VIEW hard auth
  -> 只有通过 hard auth 的 evidence 才能进入 prompt
```

也就是说，预计算 ACL projection 是检索准入，resource-service hard auth 是 prompt 前防陈旧兜底，两者不能互相替代。

### 3. 敲定了 RAG 主方案

长期方案文档落到了：

- `docs/plans/rag/02-rag-resource-permission-model.md`
- `docs/plans/rag/03-rag-complete-solution.md`
- `docs/plans/rag/05-rag-final-solution-deck.html`

最终方案主线是：

```text
长期知识库 Corpus
  -> parent-child chunking
  -> Context Indexing
  -> Qdrant dense retrieval + Elasticsearch lexical retrieval
  -> application-side fusion / upstream score fusion
  -> rag.knowledge_search ranking post-process
  -> Context Builder
  -> prompt 前 resource-service VIEW hard auth
  -> answer with citations

旁路增强：
seed chunks
  -> bounded concept graph expansion
  -> evidence chunks
  -> Context Builder
```

几个定稿边界：

- RAG 是长期业务索引体系，不是 `cnt_*`、`tfile_*`、`web_content_cache`。
- `chunking_engine` 和 `ranking_engine` 只做基础能力，不承载权限、持久化、抓取或工具输出。
- 图谱只做旁路 evidence expansion，不默认把完整图谱交给模型。
- `knowledge_search` 工具后续只是薄门面，主逻辑放 `application/rag/`。

### 4. 论文路线也做了取舍

今天重点看了三篇论文方向：

- InSemRAG
- Grounded Decoding
- Predictive Prefetching

最终没有保留论文精读材料，因为我们不在乎论文复述本身，只吸收对设计有用的部分。

最后敲定：

- 只采用 InSemRAG 里的“意图感知检索”思想。
- 具体落地不是小模型隐式路由，而是主模型显式选择 retrieval profile。
- Grounded Decoding 第一版不采纳。
- Predictive Prefetching 第一版不采纳。

这里延续了昨天 web search 重构后的经验：小模型做隐式路由、自动 query 改写、自动多跳检索收益低，且容易过早收窄搜索面。主模型有完整上下文，更适合做高层意图选择；服务端负责确定性执行。

定稿 profile：

```text
balanced
semantic
lexical
anchored_exact
```

同时明确了一个很关键的判断：BM25 可以承担 lexical relevance，但不能单独承担“精确检索”。`anchored_exact` 必须由 `must_terms`、`quoted_phrases`、keyword 字段和 hard constraint 一起实现。

### 5. Context Indexing 改成必须走小模型

今天中间对 Context Indexing 做了几轮收敛。

一开始还考虑过 deterministic fallback，但最后明确不要这么做：

- `context_summary` 不能靠规则可靠生成。
- `important_terms` 也不能靠规则稳定抽取。
- `parent_summary`、`previous_summary`、`next_summary` 这类上下文更不应该失败后硬凑。
- fallback 质量参差会污染长期知识库，后面很难清。

所以定稿为：

```text
Context Indexing 必须调用小模型。
失败就让入库任务可重试。
不写 deterministic fallback。
```

代码上也落了初步占位：

- `src/chat/application/rag/ingestion/context_indexing.py`
- `src/chat/application/rag/ingestion/models.py`
- `tests/rag/test_context_indexing.py`

当前输入要求：

```text
parent_text
child_text
document_title
section_path
```

`parent_text` 是 child 所在父块全文，给小模型判断 child 的局部语义位置和术语边界。输出中 `evidence_text` 保留原始 child 文本，`indexing_text` 用于 embedding、Elastic lexical 和图抽取消歧。

同时删掉了 `used_llm` 字段，因为现在 LLM 是硬约束，不是可选能力。

验证结果：

```text
python -m pytest services/wisepen-chat-service/tests/rag/test_context_indexing.py -q
```

通过：`3 passed`。

### 6. 注册了 RAG 专用 ranking engine

今天也在 `ranking_engine` 里占了一个 RAG 专用 engine：

```text
rag.knowledge_search
```

位置：

- `src/chat/application/utils/ranking_engine/registry.py`

这里有一个重要取舍：Qdrant 和 Elasticsearch 本身已经各自打过分，上游 RAG orchestrator 会做融合或按融合顺序传入候选，所以 `rag.knowledge_search` 不再重复做 BM25 / dense 打分。

它当前只负责 post-process：

- ZeroEntropy reranker
- MMR 多样性控制

这避免把业务检索规则塞进通用 ranking engine，也避免重复计算上游已经完成的分数。

## 最终状态

今天 RAG 这条线已经从“调研和纠结”进入“第一版可以开始实现”的状态。

定稿口径是：

```text
Chunk RAG 主线。
Concept Graph 旁路。
主模型做意图路由。
Context Indexing 必须小模型。
Qdrant + Elasticsearch 双路检索。
RAG ranking engine 只做后处理。
resource_id 是权限根。
VIEW 是第一版查询权限。
ACL projection 是检索前强制准入。
Context Builder 是 prompt 注入唯一入口。
```

下一步如果继续做 RAG，建议顺序是：

1. 定义 RAG DTO 和状态枚举。
2. 实现 `RetrievalPlanBuilder`。
3. 实现 ACL projection 和 filter builder。
4. 接 parent-child ingestion。
5. 接 Qdrant / Elasticsearch repositories。
6. 做 hybrid retrieval orchestrator。
7. 做 Context Builder。
8. 最后才写 `knowledge_search` 工具门面。

今天感觉最值的一点，是把很多“看起来高级”的支线都按掉了。主链越清楚，后面代码越不容易长歪。
