# 原生文件编写总计划

## 1. 文档定位

本文档定义 WisePen 后续“原生文件编写能力”的统一边界。

它负责回答以下问题：

- 什么叫“原生文件编写”
- 哪些格式走直接写文件
- 哪些格式必须有正式校验
- DOCX、PDF、HTML、Markdown、图片和其他文件格式之间如何分工
- 绘图、文档编写、文件导出如何纳入同一能力域

本文档不展开到单一格式的细节实现；具体细节见后续子计划。

## 2. 总目标

后续沙箱接入后，系统需要具备一套统一的文件编写能力，满足：

- 能直接写代码生成目标文件
- 能输出真实可下载产物
- 图像既能单独交付，也能嵌入 DOCX 等文档
- 支持多种文件格式
- 对有成熟工程校验手段的格式执行正式校验

这套能力不以“模型直接吐文本”作为交付终点，而以“代码生成的文件产物 + 校验结果”作为终点。

## 3. 核心原则

### 3.1 原生优先

对主要格式优先使用该格式的原生编写方式：

- DOCX：原生 OOXML / `python-docx` 路线
- PDF：定义为 `DOCX -> PDF` 链路
- HTML：直接生成 HTML
- Markdown：直接生成 Markdown
- 图像：直接生成 PNG / SVG / PDF 等图像文件

### 3.2 不把 PDF 当独立富文档编辑主线

PDF 在本规划内不是独立的富编辑目标格式，而是：

- DOCX 能力的导出链路
- 图表等可视化产物的独立交付格式

换言之，正式排版文档的主编辑格式是 DOCX，PDF 只是成熟导出形式。

### 3.3 统一按“格式能力成熟度”决定校验

所有文件格式都允许直接写出到磁盘。

但只有这些格式被明确纳入正式校验链：

- `docx`
- `pdf`
- `html`
- `md`
- 以及其他“确有成熟校验手段”的格式

其它格式：

- 允许直接生成
- 但默认不承诺完整格式级验收
- 可以只做最小存在性与扩展名/MIME 检查

### 3.4 图像是一级产物

图像不是 DOCX 的附庸。

绘图能力必须支持：

- 单独输出图片文件交付
- 作为中间产物被 DOCX、HTML 等引用或嵌入

### 3.5 沙箱执行代码，但不本地部署模型

本能力可以随意引入工程依赖，只要：

- 不要求本地部署模型
- 不强依赖 Docker 编排
- 云端 LLM 或第三方 API 依赖若成本可接受，可以评估接入

## 4. 能力分层

建议统一拆为 4 层：

### 4.1 File Intent Layer

负责表达“用户要什么文件”：

- 目标格式
- 内容结构
- 风格要求
- 是否可视交付
- 是否需要校验

### 4.2 Builder Layer

每种格式对应自己的 builder：

- `DocxBuilder`
- `PdfExportBuilder`
- `HtmlBuilder`
- `MarkdownBuilder`
- `ImageBuilder`
- `GenericFileWriter`

### 4.3 Validation Layer

统一对可校验格式执行：

- 结构校验
- 渲染校验
- 文件完整性校验
- 视觉/版式校验

### 4.4 Artifact Layer

统一管理产物：

- 输出路径
- 中间文件
- 引用关系
- 可嵌入资源
- 最终交付对象

## 5. 格式策略

### 5.1 DOCX

- 主富文档编辑格式
- 原生写作
- 正式校验

### 5.2 PDF

- 定义为 `DOCX -> PDF` 导出链
- 复用 DOCX 编辑能力
- 使用成熟社区转换方案
- 做正式校验

### 5.3 HTML

- 直接写 HTML
- 可通过 DOM/HTML parser 校验
- 若有需要可做截图/浏览器渲染验收

### 5.4 Markdown

- 直接写 Markdown
- 可做 parser 级校验
- 可与渲染预览联动

### 5.5 图片/绘图

- 直接生成 PNG / SVG / PDF / JPG 等
- 可单独交付
- 可嵌入 DOCX / HTML
- 对主流绘图格式执行基本文件与渲染校验

### 5.6 其他文件

- 允许直接写出
- 默认只做轻量校验
- 若后续发现成熟校验链路，再纳入正式能力范围

## 6. 统一交付模型

建议所有文件编写能力最终返回统一结构：

- `artifacts`
- `primary_artifact`
- `embedded_assets`
- `validation_report`
- `warnings`

其中 `validation_report` 必须明确：

- 哪些格式做了完整校验
- 哪些格式只做了轻量校验
- 是否存在 render/visual QA 缺失

## 7. 依赖策略

依赖选择原则：

- 优先成熟社区库
- 优先可稳定在沙箱中执行的纯代码/CLI 方案
- 不引入需要本地模型服务的库
- 可以接受云端 LLM 或 API 依赖，但要按成本和必要性评估
